# The process environment owns the hosting environment

**Status**: Accepted

The process environment is authoritative, and an environment file is a development convenience. The template used to load `.env` before the application builder existed, with a loader that defaults to overwriting what is already set, so a deployment that set its environment correctly still booted as development: developer exception pages, the Vite development integration, and no HTTPS redirection. The file was also the only source of the hosting environment in development, which made it both decide the environment and be conditional on the environment.

The hosting environment is now read from the process *before* anything else loads, so the file can never decide the environment it is conditional on. A host names it with either `DOTNET_ENVIRONMENT` or `ASPNETCORE_ENVIRONMENT`, and the framework reads the first in preference to the second, so the bootstrap reads them the same way and then puts back the absence of either name the process did not use — otherwise a host using the general name, or a file using the name the host did not, would still be at the file's mercy. The file is read only when the process says development or says nothing, and it is loaded to fill gaps without overriding a value that is already set. The loader's default is to override, so that behaviour is stated at the call site rather than inherited. Development tooling supplies the environment for a run-from-source launch, and the example environment file no longer sets it.

An unset hosting environment is production, which is the framework's own default and the safe direction. There is no custom failure for a missing environment: loud failure stays where no safe default exists, which is the development variables. The port-integrality gate and the Vite variable requirements move behind the development check, so a production host requires nothing the template owns — the allowed-hosts value already ships in the base configuration file, which the publish output includes. Nothing environment-bearing is copied into the publish output.

Ownership, in one line: the artifact ships safe defaults, the development machine owns `.env`, the build host owns the client's production values, and the deploy host owns the server's production values.

## Considered Options

- Failing when the hosting environment is unset was rejected because production is the framework's own default and the safe direction. A missing variable should not turn a deploy into a failed one, and the failure would arrive as an outage rather than as a configuration error the operator wrote.
- Letting the environment file supply the hosting environment when the process says nothing was rejected as the circularity this decision exists to remove. The file decides the environment and is conditional on the environment; a typo in a development file would then redirect a deployment that never asked for one. The value is discarded after the file is read, so the file cannot redirect the deployment by omission either — under either variable name, since `DOTNET_ENVIRONMENT` outranks `ASPNETCORE_ENVIRONMENT` and a file setting the one the host left unused would otherwise be the one that decided.
- Reading the environment file in production when the host named it was rejected because the point of the file is to be a developer's convenience. A production host that has an `EnvFile` variable set — a leftover service definition, an old launch profile, a container image — would otherwise be one variable away from a development boot, and the symptom (a stack trace on a public error page) is exactly what the change is meant to make impossible.
- Keeping the Vite requirements in every environment was rejected because they are development requirements. A production host owns no client dev server, and asserting one anyway meant a production deploy could fail on a value it has no reason to set. The gate ran before the builder existed, so it failed a host that had configured itself correctly and completely.
- Requiring the allowed-hosts value was rejected because `appsettings.json` ships one, and the publish output includes it. A requirement the artifact already satisfies is ceremony, and the environment is not the place a deployment should be learning its own configuration from a file nobody reviews.

## Consequences

**This is a breaking change for an operator whose production `.env` supplied values by hand.** Those values are authoritative today precisely because the loader overrode the process, so the moment the file stops being read outside development, every value an operator added reverts — and it reverts at exactly the moment they set their environment variable correctly and believe the deployment is now tightened. **A green boot is not evidence the migration is complete.** The procedure is: inventory the production `.env`, diff it against `.env.example`, and move every key that is not in the example to the host — a service manager `EnvironmentFile=`, `docker run --env-file`, IIS `web.config` environment variables, or an `appsettings.Production.json`. Do it in the same change that sets `ASPNETCORE_ENVIRONMENT=Production`. The registry path override is the value most likely to be present by hand, and with ADR 0014 landed its loss is a loud startup failure rather than a silent reversion to an unprotected deployment.

A deployment that relied on the development defaults now gets production defaults, so `Vite__Server__DevServerUrl` and friends are no longer asserted outside development and nothing about a development launch is required to boot one.

A developer who sets a value in their shell now wins over the same value in `.env`, which is what they expected all along. A developer who sets `ASPNETCORE_ENVIRONMENT` in `.env` finds it ignored, and the example file says where the value comes from instead of being silently inert.

The environment file is no longer read at all outside development, so a file a developer left in a deployment is inert rather than authoritative. It also never travels with the artifact.
