# Route resolution is a client runtime API — the server routes, the client binds

The client route loader (`poyo.client/src/routes/route-loader.ts`) is template boilerplate: it globs `src/pages/**/*.page.tsx` with Vite's `import.meta.glob`, imports `routes.json`, builds the route map with `lazy()` wrappers, and provides `findRouteByName`/`findRouteGeneric` plus dev-only ghost detection — copy-pasted into every generated project, so any bug or improvement in that logic has to be shipped project by project. That is the same problem ADR 0005 solved for `usePage`, and the internal Pwo framework has already solved it for routing: route resolution ships in `@pwo/runtime` (Pwo ADR-0005), leaving the generated project a thin Vite adapter. Poyo adopts the same contract inside its own single-package model — the runtime stays a subpath of `@rubichandrap/poyo`, per ADR 0005's deliberate divergence.

**Decision**: `createRouteTable(manifest, pageLoaders, { baseUrl, dev, onWarn, onError })` ships from `@rubichandrap/poyo/runtime` as a new sibling module (`src/runtime/route-table.ts`, re-exported from the runtime index) and returns `{ routes, routeMap, findRouteByName, findRouteGeneric, detectGhostRoutes }`. It is a stateless per-load resolver: the server routes (MVC + `RoutePolicy`), the client binds — a server-declared page name (`data-page-name` on the mount root) is mapped to its lazy component and mounted into the server-rendered shell. No provider, no state, no router, no client-side navigation. Lookups return `AppRoute` (canonical path, page name, `access` from the registry defaulting to `protected`, lazy component), never a bare component, so app code never hardcodes paths or access levels. A registry entry pointing at a missing page file warns and skips only that route — one bad entry must not disable the whole bundle; an unknown server-declared name reports through `onError` in dev and renders the existing "Page not found" UI; ghost detection runs in dev. The base path is server-injected (`data-base-path` = `Url.Content("~/")` on `<body>`), with `VITE_BASE_URL` as the standalone-dev fallback only; `findRouteGeneric` strips it before URL matching. Strictness stays server-side: `RoutePolicy` throws at boot on an invalid registry.

The template keeps the Vite boundary as a thin adapter in the same file (`route-loader.ts`, ~40 lines): the glob, a re-key of glob keys into registry space (`"../pages/"` → `"src/pages/"`), base-path resolution, the `createRouteTable` call, and a re-export of the legacy surface so existing imports (`app.tsx`, `routes/index.tsx`) keep working. `RouteComponent` (Suspense + loading fallback) stays in the template — UI, not framework. `app.tsx` updates to the new contract: `findRouteByName` returns an `AppRoute`, the manual component wrapper and the hardcoded Home fallback (a lazy import that bypasses the registry) are removed, and a miss renders "Page not found" — the registry is the source of truth. The mount root id unifies to `react-root` across views (Register already uses it; Dashboard/Login/Home switch from `#root`).

`poyo generate` emits `src/routes/routes.generated.ts`: the registry as `as const satisfies readonly RouteEntry[]`, `RouteName`/`RoutePath` literal unions, and a `routePath(name)` helper. The file is gitignored — a derived artifact doesn't belong in git, and the toolchain regenerates it at every entry point so it can never lie: `route add/remove/update/sync` re-emit it after mutation, and the template client's `predev`/`prebuild` run `poyo generate`, so dev and build always work from the current registry and a scaffolded project self-heals on its first command. This requires splitting the generate command's behavior: the route manifest always emits; the OpenAPI codegen (dtos/validations) runs only when a source is provided, instead of erroring. The accepted cost is a fresh clone's editor/type-check being red until generate has run — the same trade Pwo and Nuxt make. Static links (Home/Login pages) adopt `routePath` plus a base join, so a renamed or removed route is a build error instead of a silent 404.

**Considered Options**:

- **Keep the loader entirely in the template** — Rejected: copy-pasted framework logic with no upgrade path; the whole point of a framework runtime is one home for it (the ADR-0005 argument, applied to routing).
- **Separate `@rubichandrap/poyo-runtime` package mirroring `@pwo/runtime`** — Rejected: ADR 0005 already chose the subpath model for this framework; package count is part of a public framework's first impression.
- **Vite plugin with a virtual module** — Rejected: `import.meta.glob` resolves relative to the importing module, and a plugin turns the zero-dep runtime into a build-tool integration with lifecycle surface, for no benefit over a ~40-line adapter.
- **Hard-fail the client on missing routes** — Rejected: a throw at module scope would let one bad `files.react` blank the entire bundle, and a prod throw on deploy skew just replaces an honest "Page not found" with a blank page.
- **Cast `routes.json` directly instead of codegen** — Rejected: JSON imports can never produce literal types, so compile-time route names are only reachable through a generated module.
- **Commit `routes.generated.ts`** — Rejected: the manifest is a derived artifact; committing it adds a second diff to every route change, invites merge conflicts on a regenerable file, and lets a hand-edited `routes.json` ship with a stale manifest. Regenerating at every entry point (`predev`, `prebuild`, route commands) keeps the gitignored file strictly fresher, keeps Pwo and Poyo on the same convention, and the one cost — a fresh clone's editor red until the first generate — is the same trade the internal framework already accepts. (`dtos.generated.ts` stays committed for now: its regeneration needs an external OpenAPI source, so it cannot self-heal the way the route manifest can; adopting Pwo's committed-snapshot model for the schemas is a separate change, after which the repo's convention converges.)

**Consequences**: generated projects stop carrying route-resolution logic and receive fixes through package upgrades; the runtime gains one dependency-free sibling module (`react` stays the only import source, a peer — `lazy` is a value import from it); the CLI grows a route-manifest emitter wired into `generate` and every route command, and `generate` splits its OpenAPI part (optional source) from the always-run manifest emission; the template client gains `predev`/`prebuild` regeneration so fresh clones and scaffolded projects self-heal; the template's views gain `data-base-path` and a unified `react-root`; the fixture e2e asserts the resolved package ships `dist/runtime/route-table.js` and the built bundle carries the route-table module, anchored on its `[RouteTable]` diagnostic prefix — the production minifier renames the `createRouteTable` identifier, so the literal prefix is the stable proof (red until the release version is published); docs are updated (AGENTS.md §4, READMEs, CONTEXT.md glossary — the client-side route table is a per-load binding, distinct from the Routes registry). Release mechanics are unchanged: three packages, one version, lockstep — the feature ships as the next additive minor (0.3.0) alongside the pending framework-runtime work, no bump in feature commits.
