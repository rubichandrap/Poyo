# The route manifest is encapsulated: generated types augment the runtime, app code imports the runtime

**Status**: accepted. Supersedes the committed-artifact consequence of ADR 0007 (the file returns to gitignored); ADR 0007's emit-machinery decisions stand.

`routes.generated.ts` currently leaks into app code: template pages import `routePath` from it directly, and its export surface (`routeManifest`, `RouteName`, `RoutePath`, `routePath`) is de-facto public API. That couples every app import to the file's name and location, and it is the one generated artifact the user must *see and understand*. Next.js inverts this — generated types live in `.next/types/` and users never touch them, while `<Link href>` typechecks against real routes — and TanStack Start follows the same pattern (a generator-owned `routeTree.gen.ts` that app code never imports). The common rule: **the generated file feeds the framework, never the app.**

**Decision**:

1. `routes.generated.ts` stops exporting the manifest API and instead **augments the runtime**:

   ```ts
   // routes.generated.ts — generated by `poyo generate`, DO NOT EDIT. Imported by no one.
   import type {} from "@rubichandrap/poyo/runtime";

   declare module "@rubichandrap/poyo/runtime" {
       interface PoyoRouteRegistry {
           names: "Home" | "Login" | "Dashboard" | "Register";
           paths: "/" | "/Login" | "/Dashboard" | "/Register";
       }
   }
   ```

2. The runtime owns the typed API: `type RouteName`/`type RoutePath` derive from `PoyoRouteRegistry` (defaulting to `string` before augmentation), and **`routePath(name)` is exported from the runtime**, resolved from the active route table the adapter registers at startup — not from generated code. Calling it before the table exists throws a clear error ("route table not initialized — import your route-loader").
3. App code imports only the runtime: `import { routePath } from "@rubichandrap/poyo/runtime"`. `<Link href>` accepts `RoutePath | (string & {})` — a typo'd route name is a compile error, a dynamic string still typechecks. The template's `Home`/`Login` pages move to the runtime import.
4. **The manifest returns to gitignored.** ADR 0007 committed it because its absence broke imports and killed scaffolds on fresh clones. The augmented file is imported by no one — a missing manifest just means the registry types degrade gracefully to `string` until the first `poyo generate`. The trade that justified committing it is gone; the repo's convention converges on "derived artifacts are gitignored, the registry is the only committed source."

**Why not the alternatives**:

- **Keep the committed, app-imported manifest** (status quo): rejected — it makes generated-file plumbing part of every app's public import surface and blocks any future emit change without a breaking rename.
- **Virtual module via a Vite plugin**: rejected — turns the zero-dep runtime into a build-tool integration for a ~10-line adapter's job (the ADR-0006 argument, still true).
- **A feed of generated exports re-exported through a stable barrel** (`src/routes/index.ts` re-exporting `routes.generated.ts`): rejected — it hides the leak behind one hop; the barrel's API still *is* the generated file's API.

**Consequences**: the generated file's name and location stop being API — the emitter can move or rename it without breaking an app; `RouteName`/`RoutePath`/`AppRoute` types are re-exported from the runtime; the template's `.gitignore` re-ignores the manifest and its committed copy is removed; the CLI keeps regenerating it on every route command and `poyo generate` (unchanged); editor experience on a fresh clone shows `string`-typed route names until the first generate — the standard derived-artifact trade, now uniform across both generated families.
