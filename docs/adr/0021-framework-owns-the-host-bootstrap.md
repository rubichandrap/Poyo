# The framework owns the host bootstrap

**Status**: Accepted. Extends ADR 0008's ownership argument to the builder and to the path base; states that ADR 0017 and the ADR 0014 amendment are unchanged in substance, with only their implementation location moving.

Three behaviours that belong to the framework lived in the template's `Program.cs`: the hosting environment is read from the process before anything loads (ADR 0017), the environment file named by `EnvFile` is loaded only for development or an unset environment with no-clobber semantics, and the content root follows the application's content rather than the host's working directory (ADR 0014 amendment). Each is framework behaviour, not an application's choice, and each arrived as a "copy this `Program.cs` block" changelog note — 0.6.0 alone carried three. A generated project that missed one kept the bug: a published application started outside its own directory served pages whose bundle, styles and icon answered 404, and from `/` it did not boot within a minute. The template is copied once at scaffold time, so a fix to any of them reaches an existing project only by hand.

**Decision**: the Server core exposes the builder entry point, `PoyoHost.CreateBuilder(string[] args)` in namespace `Poyo.Framework`, which returns the `WebApplicationBuilder`. It performs, in order: read the hosting environment from the process (`DOTNET_ENVIRONMENT`, else `ASPNETCORE_ENVIRONMENT`); load the file named by `EnvFile` when that environment is unset or Development, with `LoadOptions.NoClobber()`, then clear either hosting-environment variable the file introduced; choose the content root — the working directory when it holds the application's `appsettings.json`, otherwise `AppContext.BaseDirectory`, unless the host names one (`ASPNETCORE_CONTENTROOT`, `DOTNET_CONTENTROOT`, or a `--contentRoot` argument); and create the builder. The behaviour itself is unchanged: this move relocates it, it does not redesign it.

The template's `Program.cs` starts with `WebApplicationBuilder builder = PoyoHost.CreateBuilder(args);`. The project keeps what the application owns and can change without the framework: authentication and the demo cookie scheme, authorization, application services, the exception handler, CORS, the Vite services and the development-variable checks, the OpenAPI document and its snapshot export, HTTPS redirection, `AddPoyo`, `MapControllers` and `MapPoyoRoutes`. The path base is framework behaviour too, and the template applies it with `app.UsePoyoPathBase()` where it used to hold its own `UsePathBase` block; that ownership is stated below.

**The path base is framework behaviour too.** A deployment that mounts the application under a prefix — an IIS virtual directory, a reverse-proxy path — states it once in `PathBase`, and the application must apply it before static files and routing so that asset tags, the client's `data-base-path`, navigation, API calls and the authentication challenge all resolve against one `Request.PathBase`. That is a rule of the framework, not an application choice: left in the template it is one more block an existing project has to copy before it receives a fix, which is the problem this decision exists to remove. `PoyoHost.UsePoyoPathBase(this WebApplication app)` reads `configuration["PathBase"]` once and calls `UsePathBase` only for a non-blank value, so an unset or blank value applies nothing and a root deployment is unchanged. The call belongs in the same middleware position the template's block occupied — before `UseDefaultFiles`, static files and routing. A project that keeps its own `UsePathBase` block still works and behaves as it does; adopting the call is optional, and the template's changelog names the block it replaces. Nothing else about the base changes: the framework does not normalize or validate it, add a redirect, or take over routing or the client's URL handling.

**DotNetEnv is a requirement of the server project.** The environment file's parsing stays on DotNetEnv, as it was in the template: quoting and variable-expansion details are behaviour users rely on, and a built-in parser would change them. Because the Server core now calls the library, a project that compiles the core needs the package reference. The build guard that already fails when the server core is missing from `node_modules` also fails, naming DotNetEnv, when that reference is absent — an existing project that updates the package without it gets an instruction instead of a compile error inside a linked file.

**Why the alternatives were rejected**: leaving the bootstrap in the template is the problem this decision exists to remove; a static helper copied into each project reintroduces the frozen copy; a bootstrap that reads only the environment and not the content root would split one decision across two places, which is what made the rule drift from its tests before.

**ADR 0017 and the ADR 0014 amendment are unchanged in substance.** The process still owns the hosting environment; the file is still development-only and no-clobber; the content root still follows the content, and a host-named root still wins. Only the code that implements them moves from the template into the framework package, and with it the upgrade path: a fix arrives with `pnpm update @rubichandrap/poyo` rather than as a manual edit. ADR 0014's registry-resolution chain is untouched: `AddPoyo` still resolves `Routes:JsonPath` against the content root the bootstrap chose.

**Verified**: the existing server suites pass unchanged against the new bootstrap — hosting environment, published application (publish directory, unrelated directory, filesystem root, with assets), registry override, startup failure and subpath deployment. A published-application test was added for a host-named content root: the published output is started with `ASPNETCORE_CONTENTROOT` pointing at a directory with its own `wwwroot`, and a file that only that directory carries is served. The path-base suites run unchanged through `UsePoyoPathBase`: the document mount attribute, static assets, the API and the auth redirect under `/Poyo`, the guest redirect under the base, and the release fixture's Link/Back/Forward check in Chromium at the root and under `/Poyo`. A blank `PathBase` case was added: the application answers at the host root exactly as it does when the value is unset.
