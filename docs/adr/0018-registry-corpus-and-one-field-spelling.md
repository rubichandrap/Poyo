# A field has one spelling, and the two runtimes prove they agree

**Status**: Accepted

ADR 0015 defined a route's identity once and enforced it in two runtimes: the server, at boot, and the framework package's route manager, on every read and write. That made the *rules* one thing and the *enforcement* two, and left the agreement between them asserted rather than proven. The rules are written twice — once in C#, once in TypeScript — because the two runtimes refuse a bad registry at different moments, the CLI when it is authored and the server when it is deployed. Two suites that each assert their own wording cannot detect the wording drifting apart, and they had already drifted: an absent `access` and a `"controller": null` were each found by a two-axis review rather than by a test.

A **registry corpus** now makes the agreement falsifiable. `fixtures/registry/` holds one file per rule — a registry and the verdict it earns — and both runtimes read all of it. A rule added to one runtime and not the other turns the other one's suite red, at the same commit, in the same command. A case that declares one verdict asserts the message fragments both runtimes are expected to carry, so the two name the same facts; a case that declares a verdict per runtime pins a difference that is deliberate rather than closing it, and carries no shared wording because a difference of answer is not a difference of wording.

A case that declares one verdict and no fragments is the third shape, and the one the format cannot do better: both runtimes refuse the registry and neither can say it the way the other says it. A file that is not JSON is refused by the server as a schema failure and reported by the route manager as a read failure, and a shared fragment would have to name one of those to be shared at all. Such a case holds only what the two agree on — that both refuse — and the server's wording for it is pinned outside the corpus, in the suite that has a reason to name the message the boot prints. The route manager's is not pinned anywhere, because nothing in the CLI's contract turns on the sentence: it is a parse failure, and the sentence only has to say where it came from.

The corpus lives at the repository root, owned by neither package. `packages/poyo` must not read files out of `poyo-template`, and the template's test project must not read them out of a published package, so a home inside either package would couple one to the other in both directions. It is read only at test time, so neither published artifact depends on it and nothing that ships carries a copy.

Two registry states are *file* states rather than declarations, and stay where they are: a file that is not there, and a file with no content. Neither is expressible as a registry, and both are already told apart by their own messages.

A **field has one accepted spelling** — and so does its value, since `{"access": "Public"}` is the same hazard one level down. The server says so itself. The deserializer's property matching is case-insensitive because that is how a lower camel case registry maps onto a PascalCase model at all, which meant `{"Path": "/Home"}` and `{"Access": "public"}` were accepted where the route manager refused them: two spellings for one field across the three runtimes that read the registry, so a rule written once meant two things. The server now checks field names, the members a route must carry, and the two values whose type is part of the contract, on the raw JSON before the deserializer sees it. A mis-cased member is an unknown member, and a route with no `files` is refused at boot instead of deserializing to a null that surfaced when the routes were mapped.

The order of those checks is the order of how much each says. A **mis-spelled `dynamic` with a non-boolean value is reported for the value**, with the spelling it was written in beside it: a mis-spelled name is a symptom, a wrong value is the mistake, and the operator has to edit the text they wrote. Before this, the case-sensitive lookup missed the field entirely and the generic parse failure answered instead — the one message that names neither the field nor the route.

## Considered Options

- **Leaving the agreement asserted was rejected.** The claim is the whole point of holding the registry to a canonical form: a contributor learns about a bad registry when they author it, not when they deploy it. If the two can drift, the CLI accepts a registry the server refuses, and the contributor learns at deploy time — the exact outcome the route manager exists to prevent.
- **A shared rule table both runtimes read was rejected.** It would have been genuinely one definition, but the server's rules ship as C# source inside the framework package and the route manager's as TypeScript, and a table would have to ship in both published artifacts and be read at runtime. A registry contract that ships twice, in two formats, is a second thing to keep in step — the corpus makes the duplication checkable, which is what was missing.
- **Putting the corpus inside `packages/poyo` was rejected** because the template's test project would then read it out of a published package's directory — through `node_modules`, in a path that changes shape between a workspace link and an installed tarball. Putting it inside `packages/poyo-template` was rejected for the mirror reason: a published package reading another published package's files.
- **Generating the corpus was rejected.** A generated corpus is only as good as the generator, and a reviewer reading a generated case cannot tell a rule from a typo. The cases are the artifact; a case is one small file.
- **Making the C# reader case-sensitive was rejected**, and this is the question the ticket left open. `PropertyNameCaseInsensitive = false` does not map a lower camel case registry onto a PascalCase model at all — every field became unmapped and every registry was refused — so a naming policy would be needed in its place, and `JsonNamingPolicy.CamelCase` spells `JsonLd` as `jsonLd`, which is not what the registry writes. Pinning one JSON name per property would have made a .NET member's spelling decide a registry field's spelling, which is the model's business leaking into the contract. The one-spelling rule is a property of the registry, so it is stated in the registry's own check, where it can also be reported with the route beside it.
- **Refusing a mis-spelled `dynamic` as an unknown field, on the strength of the one-spelling rule alone, was rejected** for the case where the value is also wrong. `{"Dynamic": "junk"}` is two mistakes; the message that names the value and quotes the spelling fixes both, and the field-name message would name one and leave the other for the next boot failure.
- **Checking the blankness of a file path on the server was rejected**, continuing ADR 0015: a file path is not a route's identity, and a blank one fails when the route is requested. The server now checks that the members it reads are *present and typed*, and judges no value. The route manager, which resolves the React page as well as the view, still requires both to be non-blank. That difference is four corpus cases rather than a rule either side lost — two pinning it, two saying where blankness stops being the question — and the first version of this ADR claimed a case existed before one did, which is the failure the corpus itself exists to prevent, caught in review instead.
- **Checking the `seo` payload in the route manager was rejected.** The route manager treats `seo` as opaque, and the server is the only runtime that reads it, so the payload's shape is the server model's concern alone — checking it in the route manager would model it twice to police a member the CLI never interprets. Two corpus cases pin where that boundary falls: both runtimes accept a `seo` member spelled any other way, because the deserializer's property matching is how the .NET model is spelled, and the server alone refuses a member its model does not know, at the boot rather than when the registry is authored. Both halves are stated in cases rather than left implied, and the cost of the trade is the operator who misspells a `seo` key finds out at deploy time.
- **An authored `"seo": null` is read as undeclared, on both sides.** The corpus found the route manager refusing it where the server's `SeoModel?` took it as "no SEO", which is the same reading ADR 0015 pinned for `"controller": null`: a null is a declaration of absence, not a declaration nothing can act on. The route manager was the side out of step, by its own precedent.

## Consequences

The server refuses a registry it used to boot, and each refusal names the offending route and value: a member spelled any other way, a route with no `files` or no `files.view`, an `access` that is not one of the three values, a `dynamic` that is not a boolean. A registry written with `{"Path": ...}` or `{"Access": ...}` no longer starts; the message says the member is unknown and names the route, so the fix is the field's spelling. Nothing a generated project writes changes — a scaffolded registry is already canonical and lower camel case — so no migration step is needed.

The route manager's failure messages now name the route they are about wherever the route is readable, including a route with no readable `path`, which is named by its name instead. It also refuses an array where an object is required, reads a blank or unrooted `path` as one rule rather than two, and no longer refuses an authored `"seo": null` — the corpus found it refusing one the server serves, by the same rule it already followed for `"controller": null`.

Eighteen per-rule fixtures and the tests that read them are gone from the template's test project: a rule that has a fixture here and a corpus case there has two sets of wording, which is the hazard this decision removes. What remains is a registry no rule decides — the ones a test boots a host from — plus the two file states a case cannot declare, a file that is not there and a file with no content. The registries the contract refuses are the corpus, and `StartupFailureTests` boots every one the server is said to refuse, so no rule is boot-tested in one place and reader-tested in another. The two fixtures that declared a registry with no routes, and a file that is not JSON, went with them: both were cases, and a rule's message is written down once or not at all.

The corpus is the enforcement, so the workflow is part of the contract: **a validation rule lands with its case.** A rule added to one runtime with no case pinning it is the one way the mechanism can be defeated, and it is caught in review rather than by a test — which is the honest limit of a corpus. It is a real improvement over the status quo, where the same omission produced two suites that could both be green and wrong, but it is a workflow rule and not a proof.

A pinned case is a deliberate difference and is a maintenance obligation: if the difference stops being right, the case is where that is discovered. There are four today. The **empty registry**: the route manager reads and writes a registry that may legitimately be empty, which is what `poyo route add` creates before the first route, while the server refuses to boot on one because a registry declaring no routes switches off the access model, the SEO policy and the `private, no-store` guarantee (ADR 0014). A **`seo` member the model does not know**, which only the server refuses, because only the server reads the payload. And the two halves of the **file-path boundary ADR 0015 chose** — a route with no `react`, and a route with an empty `view` — which the route manager refuses because it resolves those paths, and the server serves, because it requires the members it reads to be present and typed and judges no file path's value. A *whitespace-only* `react` or `view` is accepted by both, because the route manager checks a file field for presence rather than importing the identity notion of blank into it — so the split is presence against absence, not blank against present, and two shared cases say so beside the two that pin it.

That count is the one number here a change to the corpus can falsify, and it was wrong in three places while it was right in none: the two cases the boundary pins are two, not four, and the whole boundary is four cases with the two shared ones. The claim survived review twice because reading it meant counting the cases it described rather than the ones the directory holds — the same drift this decision set out to remove, one level up.

That last distinction was not written down before the corpus checked it. The first draft of this decision described three pinned cases for file paths, on the reasoning that a missing member, a blank one and a whitespace-only one were three shapes; running the corpus showed the route manager accepts the third, because it has always checked a file field for emptiness rather than blankness. The claim was wrong in the direction the corpus exists to catch — a registry the two runtimes would have disagreed about, described as if they agreed.

The `seo` and file-path boundaries are the ones a contributor is most likely to trip over, so they are cases rather than prose: both suites read them, both are held to the *different* answers the cases record, and closing one means deciding it and moving both sides.
