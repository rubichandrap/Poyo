# The framework package owns the client runtime (usePage)

`usePage` — the accessor for server-injected page data — currently lives in the template as a local hook (`poyo.client/src/hooks/use-page.ts` plus a `window.d.ts` declaring `SERVER_DATA?: any`), copied wholesale into every generated project. The channel it reads is a framework contract: the server sets `ViewBag.ServerData` as System.Text.Json serialization output, `_Layout.cshtml` injects it into `window.SERVER_DATA` via `Html.Raw` (the default encoder's HTML-sensitive escaping is what keeps the channel XSS-safe), and the client reads it once per page load — a one-shot bootstrap, no reactivity, fresh data flows through the API path. But the accessor itself was app code: every generated project carried a private copy with no upgrade path, and framework code masqueraded as user code. We decided the accessor belongs to the framework, shipped from the framework package — the same model Next.js uses (`useRouter` from `next/router`, not from the template).

**Decision**: `usePage` lives in `@rubichandrap/poyo` — the existing framework package — as a subpath export `./runtime`, alongside the package's CLI face (`poyo` bin, main export). The package owns the global typing: it declares `Window.SERVER_DATA?: unknown` (upgraded from `any`), and the template's `src/types/window.d.ts` is deleted. The template's client declares `"@rubichandrap/poyo": "workspace:*"` in devDependencies (the client is Vite-bundled, all deps are dev deps), and the scaffolder rewrites it to the release version at generate time, mirroring the root-level rewrite it already performs for the project CLI. `src/hooks/` is deleted from the template; the Dashboard demo imports from `@rubichandrap/poyo/runtime`. No new package: the release pipeline stays three packages, one version, lockstep.

**Considered Options**:

- **A separate `@rubichandrap/poyo-runtime` package** (mirroring the internal Pwo framework, which ships `@pwo/runtime`) — Rejected: Poyo's philosophy is minimal, and its entire client API today is one function; a dedicated package, README, changelog, and release entry for it is over-engineering, and package count is part of a public framework's first impression. The only real advantage was consistency with Pwo, which is an internal deployment and is free to follow this model later by folding `@pwo/runtime` into `@pwo/cli`.
- **`usePage` in the template, as today** — Rejected: framework code copied into every generated project cannot be upgraded independently; the whole point of the move is that generated projects resolve the accessor from npm at a real version.
- **Pinned release version in the template's client instead of `workspace:*` + rewrite** — Rejected: a forgotten bump silently resolves the stale published version in workspace dev (works in my machine, breaks elsewhere), and the lockstep release check only asserts package versions, not dependency declarations inside the template, so the drift would go uncaught. `workspace:*` fails loud at generate time if the seam breaks, is always in sync, and matches the root-level convention already in use.

**Consequences**: generated projects get the accessor from `@rubichandrap/poyo` at the release version, rewritten by the scaffolder; the new client-level rewrite seam is covered by `scaffold.test.ts` and by a fixture e2e that scaffolds a real project, installs from npm, and asserts the package resolves and the bundle carries the accessor (the fixture is red until the version is published — the npm resolution proof). The framework package gains two faces — a Node CLI and a browser-safe runtime module — so the runtime module must stay dependency-free and `react` becomes a peerDependency. Existing generated projects are standalone copies and are unaffected; the divergence from Pwo's `@pwo/runtime` is deliberate.
