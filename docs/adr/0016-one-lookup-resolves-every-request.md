# One lookup resolves every request

**Status**: Accepted

"Which route serves this request" is answered one way: `RoutePolicy.Find`, by normalized request path (ADR 0015). Every server seam that needs the answer — the access filter, the SEO filter, `PageController`, and `ControllerExtensions.PoyoPage` — asks that lookup and nothing else. The conventional `controller/action` lookup and its access-priority ordering are gone, and so is the conventional fallback route that made it reachable. The Routes registry is therefore the single source of truth for route existence, and a page has exactly one URL: the one the registry declares.

## Considered Options

- **Keeping the controller/action lookup alongside the path lookup was rejected** because the two could disagree, and the disagreement was invisible. A conventional URL resolved to no route by path, so the page controller and the controller extension saw null while the access filter still named a registry route by controller and action. That route was the only one that resolved, and it is the whole of the problem: the page rendered through an action no registry route authorized, so it answered no navigation descriptor and set no `Vary: X-Poyo-Navigation`, and the client could never navigate to it by name. Executed rather than read: probed against the template registry, an anonymous `/Page/Index` returned 500 — the view path and the route were both null, so view resolution failed — while a registry whose protected routes share that defaulted controller challenged the same URL instead. Which of the two you get is a function of the registry, which is what makes the seam hard to see: a 500, a challenge, and a guest redirect all look like ordinary responses. The access filter's `private, no-store` did apply on the paths where its lookup resolved; where no registry route shared the conventional controller and action, the lookup returned null and the URL got no access model and no privacy policy at all. A response that looks like a normal access decision is the worst way for a gap like that to present itself.
- **Keeping the controller/action lookup with no fallback route was rejected** because it has no legitimate caller. It existed only to resolve a conventional URL backwards into the registry; with the conventional URL unreachable, the filters were the only users left, and they had a path to ask with. Its access-priority ordering (protected above guest above public) and the list-order tie-break between routes sharing a defaulted controller went with it, because a caller with no conventional URL has nothing to disambiguate.
- **Keeping the fallback route but making the filters path-only was rejected** because it would have left a URL that reaches a page action with no registry route behind it — no access model, no SEO, no descriptor, no privacy policy — and no test asserting that any of it. The route is the thing to remove: the registry is the source of truth for route existence, and a route nobody declared should not have a URL.
- **Replacing the fallback route with a catch-all that 404s explicitly was rejected** as ceremony. Routing already answers an unmatched path with a 404, and the comment claiming the fallback provided a clean 404 was false — it provided a reachable page action.
- **Failing a registry route whose controller has a conventional URL was rejected** as unfalsifiable at authoring time. Every custom controller has a conventional URL by construction; the decision is about whether a host publishes it, and the registry cannot know that. The template's pipeline is where the choice is made, and `MapPoyoRoutes` documents it.

## Consequences

A link to `/Controller/Action` for a page route, and to `/Page/Index` for the defaulted page controller, now returns 404 in both anonymous and authenticated states. An operator with such a link in the wild — a bookmark, a search result, an old email — gets a clean 404 instead of a page, which is the migration note's whole content. A custom controller's page is reachable only at its declared registry path, so the client's `routePath()` and the URL the server serves are the same string.

Every URL that reaches a page now carries the same guarantees: access enforcement, registry SEO, the navigation descriptor, and `Cache-Control: private, no-store`. There is no weaker path to a page, and no page action that a registry route does not authorize.

`RoutePolicy.FindForRequest` is removed from the framework package's public server core, so a consumer calling it directly must call `Find` with a request path. The access filter no longer reads the action descriptor, so a registry route reached through a conventional URL is no longer a case it can produce — which is the point, because it can no longer be produced at all.

Removing the fallback route does not depend on error handling: the exception handler writes its response directly, there is no status-code-pages middleware and no shared error view, and API controllers are attribute-routed. An unmatched path is answered by routing, before any framework filter runs.
